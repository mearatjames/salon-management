# Quickstart: Itemized Square Terminal Checkout

**Feature**: `051-square-itemized-order`

A walkthrough of the smallest end-to-end loop that exercises this feature once the implementation lands. Use this to verify your local environment, and as the order of operations in the task list.

## Prerequisites

- Local Supabase running (`supabase status` shows a started stack).
- `.env.local` populated with Square sandbox OAuth credentials (preview-equivalent).
- A Square sandbox account with at least one paired terminal device (or the local Square HTTP stub running, per `tests/e2e/_square-stub.ts`).
- The feature branch checked out: `git checkout 051-square-itemized-order`.
- Migration `0024_square_order_id.sql` applied locally: `supabase db reset` (which re-applies all migrations including this one).

## Implementation order

The task list will be generated by `/speckit-tasks` and will follow the order below. The key sequencing rule: **write the failing tests first**, then the wrapper, then the action wiring, then the e2e tweaks. This satisfies Constitution Principle IV.

1. **Migration first** — `supabase/migrations/0024_square_order_id.sql` adds `payments.square_order_id` and `square_oauth.location_id`. Land this alone is harmless (both columns nullable).
2. **Type extension** — extend `TicketItemRow` types and the existing `lib/db/` typed wrappers if needed so `select id, kind, name_snapshot, unit_price_cents, qty, discount_target_line_ids` is type-safe.
3. **Vitest unit tests (failing)** — write the eight cases in `tests/unit/square/terminal-checkout.test.ts` plus the three in `tests/unit/square/order-cancel-orphan.test.ts`. Confirm they fail.
4. **Mapping helper** — write `mapTicketItemsToOrderLineItems` in `lib/square/orders.ts` so cases (a)–(h) pass.
5. **`createOrder` + `cancelOrder` wrappers** — flesh out the rest of `lib/square/orders.ts` so cases (i)–(k) pass.
6. **`getSquareLocationId` helper** — add to `lib/square/oauth.ts` per Research R1.
7. **Server Action wiring** — extend `sendCardToTerminal` in `app/(studio)/checkout/actions.ts` per the server-actions contract.
8. **Square HTTP stub** — extend `tests/e2e/_square-stub.ts` to intercept `POST /v2/orders` and `PUT /v2/orders/:id`.
9. **Playwright e2e extensions** — add assertions (l), (m), (n) to the existing card-payment specs.
10. **Run the local gate set in CLAUDE.md order**: `npm run format:check && npm run lint && npm run typecheck && npm test && npm run test:e2e`.

## Smoke test (manual)

After the implementation is in place, you can verify the loop end-to-end on a real Square sandbox:

1. Open the Studio checkout for a fresh ticket containing two services (one $45 gel manicure + one $60 pedicure) and a `10% off` discount applied to the whole ticket.
2. Tap **Send to Card Terminal** and complete the prompt on the paired sandbox terminal.
3. Open the Square sandbox dashboard. The corresponding charge MUST show:
   - Two line items: "Gel manicure $45.00" and "Pedicure $60.00".
   - One discount: "10% off -$10.50".
   - Grand total: $94.50.
4. Print or email the Square receipt and verify it carries the same itemization.
5. Inspect the `payments` row in Supabase: `square_order_id` is set, `square_terminal_checkout_id` is set.

## Negative test (manual orphan-cancel)

To verify the best-effort orphan-cancel path:

1. Temporarily block egress to `connect.squareupsandbox.com/v2/terminals/checkouts` (e.g., a hostname allowlist that excludes the terminal endpoint but allows `/v2/orders`).
2. Trigger a single-tender card sale. `orders.create` succeeds; `terminal.checkouts.create` fails.
3. The Studio surfaces the standard "Could not reach Square — try again" error.
4. The Square dashboard, refreshed a moment later, MUST show the Order in `CANCELED` state (not just `DRAFT` or `OPEN`).
5. Application logs MUST contain a `console.warn` mentioning `orphan order cancel` only if the cancel call itself failed; on the happy-failure path (cancel succeeds), no warning is logged.
