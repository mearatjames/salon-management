# Implementation Plan: Gift Card Redemption & Split-Tender Checkout

**Branch**: `018-gift-card-split-tender` | **Date**: 2026-05-17 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/018-gift-card-split-tender/spec.md`

## Summary

Extend the existing checkout (cash + card-on-terminal from feature 015) with a third payment method — Square gift card — and a multi-leg split-tender composition mode. Front desk taps the new **Gift card** tile, enters the GAN on a numpad sheet, sees the live Square balance, and either covers the whole ticket (Story 1) or charges the available balance and auto-flips the cart into split mode with a pre-populated owed-amount leg (Story 3). Independent of gift cards, a new **Split** affordance lets the operator compose 2+ legs (cash / card / gift) for any ticket and activate them one at a time (Story 2). Pending unactivated legs ("drafts") persist server-side so a reload or a device switch restores composition. The cart freezes while any leg is in-flight; webhook completion (card terminal or gift-card payment) flips the ticket to paid only when succeeded legs sum to `tickets.total_cents`. Concurrency safety, idempotency, and audit logging are enforced both at the application layer and at the database layer.

**Technical approach**: introduce one new server module `lib/square/gift-cards.ts` (wraps Square's `giftCards.retrieveGiftCardFromGAN` + `payments.create` for gift-card charges), extend the existing webhook handler at `lib/square/webhooks.ts` to dispatch `payment.updated` events (gift cards) in addition to `terminal.checkout.updated` (card terminal). Schema changes ship as `supabase/migrations/0010_gift_card_split_tender.sql`: a new `gift_cards` cache table (per `docs/system-design.md` line 192); the `payment_method` enum gains `'gift'`; the `payment_status` enum gains `'draft'` (the "composed, not yet activated" state for split-tender legs); `payments` gains two nullable columns (`gift_card_id uuid` FK and `square_gift_card_id text`); a new unique partial index `payments (ticket_id) WHERE status = 'pending'` enforces FR-019a + FR-022 (at most one in-flight leg per ticket) at the database level; three new atomic RPCs (`pos_compose_payment_draft`, `pos_remove_payment_draft`, `pos_activate_cash_draft`, `pos_record_gift_payment`) wrap the leg-lifecycle transitions including ticket-paid-flip and audit-log emission, mirroring the existing `pos_record_card_payment` shape from feature 015. Cart-edit invalidation (the spec's edge case "edits invalidate pending unactivated legs") happens inside the existing `addServiceLine` / `removeLine` / `setLinePrice` / `addDiscountLine` / `removeDiscountLine` server actions: each calls a small helper `discardDraftLegs(ticketId)` before the line mutation. The waiting screen reuses `lib/realtime/payments.ts` from feature 015 (no new Realtime channel added). New UI surfaces — `gan-numpad-sheet.tsx`, `gift-card-balance-sheet.tsx`, `split-cart-footer.tsx`, `payment-leg-row.tsx` — are adapted from `design-system/prototypes/transaction/FlowSingle.jsx` (split-mode toggle at line 227, payment-method tiles, and the cart-footer composition) and `numeric-keypad.client.tsx` (the existing 4-digit-PIN numpad is the visual baseline for the GAN sheet). The PaymentTiles component (`components/lacquer/checkout/payment-tiles.tsx`) gets the **Gift** and **Split** tiles enabled in this phase. No changes to OAuth, no new background cron, no second terminal device flow — gift cards are server-API charges that don't talk to a physical device.

## Technical Context

**Language/Version**: TypeScript 5 on Node.js 24 (Next.js 16 App Router; Server Components + Server Actions; Vercel Functions on the Node.js runtime — no Edge functions, per `vercel:knowledge-update` defaults).

**Primary Dependencies**: Next.js 16, React 19, `square@^44.0.1` (already in `package.json` — no version bump, already exposes `client.giftCards.retrieveGiftCardFromGAN` and `client.payments.create`), `@supabase/supabase-js` + the existing typed client wrappers in `lib/db/`, shadcn/ui (Radix primitives), Tailwind v4, `lucide-react` (icons), `zod` (Server Action input validation, in repo). **No new runtime dependencies.**

**Storage**: Supabase Postgres (hosted preview + prod). Migration `0010_gift_card_split_tender.sql` adds: one new table (`gift_cards`); two new payment enum values (`'gift'` on `payment_method`, `'draft'` on `payment_status`); two new nullable columns on `payments` (`gift_card_id`, `square_gift_card_id`); one new unique partial index for in-flight-leg-per-ticket; four new RPCs (`pos_compose_payment_draft`, `pos_remove_payment_draft`, `pos_activate_cash_draft`, `pos_record_gift_payment`); one constraint relaxation on `payments` to allow `status='draft'` (the existing `payments_cash_status_succeeded_chk` constraint says `method != 'cash' OR status = 'succeeded'` — must be relaxed so draft cash legs are allowed; it becomes `method != 'cash' OR status IN ('draft', 'succeeded')`). RLS for `gift_cards` follows the existing convention — single `select to authenticated using (true)` policy; all writes via the service-role client. Migrations auto-apply via the two GitHub Actions per CLAUDE.md / Constitution § Schema drift forbidden.

**Testing**: Vitest + Testing Library (unit) for the new Square wrappers (`gift-cards.ts` — lookup mapping for ACTIVE / PENDING / BLOCKED / DEACTIVATED states, balance extraction, error envelopes; `createGiftCardPayment` idempotency-key shape and `source_id` plumbing), the four new RPCs through their calling Server Actions with a mocked Square SDK, the cart-edit-invalidates-drafts helper, the leg-sum-equals-total guard, and the unique-in-flight-per-ticket constraint (assert a second activation race fails on `23505 unique_violation` and is caught + translated). Playwright (e2e) against a seeded local Supabase + the existing Square HTTP stub (`tests/e2e/_square-stub.ts` from feature 015, extended with gift-card lookup + payment endpoints) for the three user-story slices: US1 (full-balance gift redemption), US2 (cash + card split), US3 (partial gift balance auto-splits into a second leg). Two additional e2e specs: `gift-card-errors.spec.ts` (not-found / blocked / zero-balance edge cases) and `concurrent-charge-blocked.spec.ts` (two browser contexts on the same ticket — second activation rejected with the "ticket already being charged" message from FR-022). Audit-log assertions per the cursor-scoped convention (`newAuditCursor()` / `getAuditLogRowsSince()` from `tests/e2e/_db.ts`).

**Target Platform**: Studio web shell on desktop browsers (Chromium/Safari/Firefox latest) for the checkout flow; Vercel Functions (Node.js runtime, default 300s timeout — gift-card and split actions are all sub-second) for the existing `/api/webhooks/square` (extended to dispatch `payment.updated`), the existing `/api/square/terminal-checkout/[paymentId]` (unchanged), and a new `/api/square/payment/[paymentId]` polling fallback for gift legs that mirrors the terminal-checkout polling shape. No new cron entries.

**Project Type**: Web application — single Next.js app. Files live under `lib/square/`, `app/(studio)/checkout/`, `components/lacquer/checkout/`, `supabase/migrations/`, and `tests/`. The settings tab for Square (`app/(studio)/settings/square/`) is untouched — gift-card redemption reuses the OAuth tokens already plumbed there.

**Performance Goals**: Per SC-006, a gift-card lookup MUST resolve to a definitive balance-or-error within 3 seconds on a stable network — Square's `giftCards.retrieveGiftCardFromGAN` is a single REST call (~150–400ms server-to-Square round-trip); our action target is p95 ≤ 1500ms including Postgres upsert + audit row. Per SC-001, a full-balance gift-card checkout from tile-tap to ticket-paid is ≤ 30s — dominated by the staff typing the GAN (≈10s) and the upstream payment confirmation (≈1–3s). Per SC-002, a two-leg split-tender checkout is ≤ 90s — dominated by the customer interacting with the terminal for the card leg. Per SC-003, the partial-gift-card → next-leg transition uses one staff tap (pre-populated leg from FR-006). Cart-row re-render after a leg state change is sub-200ms (Realtime push through the existing channel from feature 015).

**Constraints**:
- **Constitution Principle I** — the GAN numpad sheet adapts `components/lacquer/numeric-keypad.client.tsx` (the existing 4-digit-PIN numpad) for a longer 16-digit input with masking after entry; the split-mode cart footer adapts `design-system/prototypes/transaction/FlowSingle.jsx:220–266` (the `tx-cart-foot` block + the inline `Split` link at line 227); the gift-card balance display reuses the muted-rose accent used by the existing terminal-tip hint (`FlowSingle.jsx:230–235`). No new tokens, no new component library, no emoji, Lucide icons at 1.5px stroke (Gift = `lucide-react/Gift`, SplitSquareHorizontal = `lucide-react/SplitSquareHorizontal` — both already imported in `payment-tiles.tsx`). The post-design auditor (`speckit-design-auditor`) runs after any phase that touches `components/` or `app/`.
- **Constitution Principle II** — every Square call is server-side. The GAN never reaches the client component as plaintext after entry — it's submitted to a Server Action which hands the canonical number to Square and returns only the balance + a UI-safe last-4 mask. The new RPCs are `security definer` + `service_role` only. Gift-card lookup and charge actions are Server Actions; the client island never imports the Square SDK.
- **Constitution Principle III (NON-NEGOTIABLE)** — idempotency keys are deterministic per the design doc: `${ticket_id}:${payment_id}` for `payments.create` on gift-card legs (same convention as terminal checkouts; both use the leg's UUID `payment_id` as the per-attempt entropy source). Webhook processing for `payment.updated` is idempotent: the update predicate is `status = 'pending'` so a replayed event is a no-op; gift-card payments use the same `payments_unique_succeeded_terminal_checkout_idx`-style backstop via a new `payments_unique_succeeded_square_payment_id_idx` partial index. Auditable transitions: `payment.draft_created`, `payment.draft_removed`, `gift_card.balance_looked_up`, `gift_card.redeemed`, and the existing `payment.captured` / `payment.failed` reused for activation outcomes. GAN values stored on disk are masked (`gift_cards.last4_mask text` — the full GAN is never persisted; the upstream `square_gift_card_id` provides the stable correlation key with Square's records — per the Clarifications session). Money invariants from Constitution Principle III are preserved: payments on a ticket still sum to `tickets.total_cents` (the split is invisible to the invariant — it's the sum of leg `amount_cents` that matters); the existing tip-split contract is unchanged.
- **Constitution Principle IV** — money-critical paths. Vitest red-first on: (a) the `lookupGiftCard` action returns distinct typed errors for ACTIVE / BLOCKED / PENDING / DEACTIVATED / NOT_FOUND so the UI can route copy without string-sniffing; (b) the `composeDraftLeg` + `removeDraftLeg` + `activateCashDraft` lifecycle preserves the "succeeded legs are immutable" invariant (attempt to remove a succeeded leg rejects); (c) the cart-edit invalidation: calling `addServiceLine` on a ticket with 2 drafts wipes the drafts and emits two `payment.draft_removed` audit rows; (d) the unique-in-flight constraint: a second `pos_activate_cash_draft` on the same ticket while one is in-flight throws the friendly error mapped from `23505`; (e) the leg-sum-equals-total guard: `pos_activate_*_draft` raises `legs_must_sum_to_total` if the sum of succeeded + pending + draft (excluding-self for activation) ≠ `tickets.total_cents`. Playwright e2e for all three user stories + the two edge specs. All red-first per the constitution.
- **Constitution Principle V** — out-of-scope items from the spec are honoured: no selling/issuing gift cards (Story 1 only redeems), no tipping changes (Tang Nails has no tip flow yet — the gift-card payment passes `tip_money: { amount: 0 }`), no digital-wallet UI changes (the existing card-on-terminal flow already covers Apple/Google Pay through Square Terminal), no refund/reversal flow (deferred to a later phase per the spec's Assumptions). No new Realtime channel — the existing `lib/realtime/payments.ts` from feature 015 already subscribes per ticket and naturally sees all leg-status updates. The cost envelope is unchanged: one schema migration (one new table, two enum values, two columns, one new index, four new RPCs); zero new dependencies; no new cron.

**Scale/Scope**: Roughly half the size of feature 015. One migration (~120 LOC SQL). One new `lib/square/` file (~200 LOC TS + tests). Six new Server Actions in the existing `app/(studio)/checkout/actions.ts` (~400 LOC added; the file already holds the cash + card actions and grows organically). Five new components under `components/lacquer/checkout/` (~600 LOC TS/TSX). Two new API routes (`/api/square/payment/[paymentId]` polling + the webhook extension at the existing `/api/webhooks/square`). ~9 new test files. Estimated 1100–1400 LOC net change including tests. Reuses every infrastructure piece from feature 015 (Square client + OAuth + webhook routing + Realtime subscription).

## Phase 0 — Research

See [research.md](./research.md). Topics resolved:

- R1 — Draft-leg state machine: where to model the "composed-but-not-activated" state (chose: new `'draft'` value on existing `payment_status` enum + reuse of `payments` table — rejected: a separate `payment_drafts` table — kept the model unified so the cart sees one ordered list of legs regardless of state).
- R2 — Idempotency key for gift-card `payments.create`: reuse `buildIdempotencyKey(ticketId, paymentId)` from `lib/square/terminal.ts` so all leg-level Square calls have one consistent shape. Validated against Constitution Principle III's "deterministic from ticket_id + payment_id" rule.
- R3 — Square gift-card lookup error mapping: which Square API responses map to which UI states (NOT_FOUND vs INVALID_REQUEST vs the card's `state` field for ACTIVE / PENDING / BLOCKED / DEACTIVATED). Confirmed via the Square SDK docs (cross-checked through context7 + `vercel:ai-gateway` agnostic of provider). The action returns a discriminated-union response — no string-sniffing in the UI.
- R4 — Concurrent-charge protection (FR-022): chose a Postgres unique partial index `payments (ticket_id) WHERE status = 'pending'` over a per-ticket advisory lock — the index is durable across processes, surfaces a clean `23505` for the action to translate, and reads "at most one in-flight leg per ticket" in plain SQL terms. Validated against the cart-freeze rule (FR-019a) which is the same constraint expressed in the client.
- R5 — Cart-edit invalidation policy: chose a single `discardDraftLegs(ticketId)` helper called from every line-mutation server action (addServiceLine, removeLine, setLinePrice, addDiscountLine, removeDiscountLine). Rejected: a database trigger on `ticket_items` — the action layer needs to emit per-leg audit rows for each discarded draft, which a trigger can't do cleanly. The action-layer chokepoint also lets each calling action surface a typed warning result (e.g., `{ok: true, draftsDiscarded: 2}`) so the UI can show a toast.
- R6 — Partial-gift auto-split flow (Story 3): chose to make the lookup-and-redeem action atomic — `redeemGiftCardWholeTicket(ticketId, gan)` looks up the card, charges what's available, and on partial balance synthesizes a fresh draft leg for the remainder in the same transaction. This guarantees the cart never sees a half-applied state and gives the UI one tap to the pre-populated second leg (satisfies SC-003).
- R7 — Gift-card webhook handling: `payment.updated` events for gift-card payments arrive via the existing `/api/webhooks/square` endpoint. The dispatcher in `lib/square/webhooks.ts` is extended to route by event type. The polling fallback at `/api/square/payment/[paymentId]` returns local DB state only (mirrors the terminal-checkout polling endpoint from feature 015) — no live Square call from the poll path.
- R8 — GAN entry & on-disk masking: chose to mask the GAN to the last 4 digits in the cache row (`gift_cards.last4_mask text`) and never persist the full GAN. The upstream `square_gift_card_id` is the durable correlation key with Square's records. Confirmed against the Clarifications session — Q1 chose "Mask to last 4 only".
- R9 — Split-mode persistence (FR-014a): drafts are rows in `payments` with `status='draft'`. They survive reload because they live in Postgres, not in client state. They are scoped per ticket and naturally restored when the ticket page loads. Confirmed against the Clarifications session — Q5 chose "Persisted server-side per ticket".
- R10 — Extending the local Square stub (`tests/e2e/_square-stub.ts`): added gift-card lookup + gift-card payment endpoints with deterministic fixtures keyed by GAN suffix so e2e tests can cover the full error matrix without a live Square sandbox.

## Complexity Tracking

> Filled because the plan introduces one new entity-type value to the audit-log vocabulary, one new value on each of two existing enums, one constraint relaxation, and the first database-level concurrency-uniqueness index on `payments`. Each warrants explicit justification.

| Change | Why needed | Simpler alternative rejected because |
|--------|------------|-------------------------------------|
| New `entity_type = "gift_card"` for `gift_card.*` audit verbs | Gift-card balance lookups and redemptions are first-class auditable events that don't fit `payment` (the lookup itself isn't a payment) or any existing entity. The Clarifications session (Q1) requires lookups to be audited with the masked GAN — the entity is the gift card, not the payment that may or may not follow. | Folding under `payment`: rejected — a "list gift-card lookups for the last 90 days" audit query would have to filter by verb prefix, defeating the prefix-equals-entity convention from feature 015. Adding it under `integration`: rejected — that prefix is for the salon's connection to Square as a whole, not for a per-customer-card event. |
| New `'gift'` value on `payment_method` enum | Required by the spec — gift card is a third payment method alongside `'cash'` and `'card'`. Square treats gift cards as a payment with `source_id = gift_card_id`, distinct from a credit-card payment. | Reusing `'card'`: rejected — auditing, reporting, and reconciliation queries all need to distinguish gift redemptions from credit-card sales (different cost-of-funds, different refund flow in the future). Square itself distinguishes them via the `source_type` field on the payment object. |
| New `'draft'` value on `payment_status` enum | Required by FR-014a — pending unactivated split legs persist server-side, but they are NOT yet pending-at-Square. They need a status that is distinguishable from `'pending'` (which means "activated and awaiting upstream") and `'succeeded'`/`'failed'`. | A separate `payment_drafts` table: rejected — would force every "list this ticket's legs" query (in the cart, on the receipt, in the End-of-Day report) to UNION two tables, and would force the legs-sum-to-total guard to query two tables. Reusing `'pending'`: rejected — the unique-in-flight index `WHERE status='pending'` would block a legitimate second draft from being composed before the first is activated. The enum-add is the smallest viable change. |
| Relaxing `payments_cash_status_succeeded_chk` from `method != 'cash' OR status = 'succeeded'` to `method != 'cash' OR status IN ('draft', 'succeeded')` | The original constraint enforced that cash payments are always immediately `'succeeded'` (no async settlement for cash). With split tender, a cash leg starts as `'draft'` (composed, not yet activated) and transitions to `'succeeded'` on activation — there is still no `'pending'` intermediate, but `'draft'` is now valid. | Dropping the constraint entirely: rejected — would allow cash legs in `'pending'` or `'failed'` states which is meaningless (cash doesn't fail asynchronously). Replacing with a different shape: rejected — adding `'draft'` to the allow-set is the minimal change that preserves the original intent. |
| New unique partial index `payments (ticket_id) WHERE status = 'pending'` | Enforces FR-019a (cart is read-only during in-flight leg) and FR-022 (concurrent charge protection) at the database layer. Two staff devices each trying to activate a leg on the same ticket will lose the race to `23505`; the application catches and translates to `TicketAlreadyBeingChargedError`. | Per-ticket advisory lock: rejected — process-scoped, doesn't survive across the application's edge cases (Server Action retries, devices switching networks). Application-only check (read-modify-write): rejected — has the classic check-then-set race the index closes. The index is durable, observable in `pg_stat_*`, and reads as plain English (`WHERE status='pending'`). |
